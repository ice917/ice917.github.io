## 形态

同一个物理量，在两个地方各写了一个常数，值不一样，而且**两处都不觉得自己错**。

这个项目的实例：

- `field.PITCH_MM = 1.0`（`field.py` L21）
- `calibrate` 用 `grid_mm = PACKAGE_MM / grid = 45 / 50 = 0.9`（`calibrate.py` L249）

原本的 P0b v3 脚本自己带了一个 `PITCH_MM = 1.0`，而 `calibrate` 算的是 0.9。

## 损伤链

```
格距差 11.1%（1.0 / 0.9）
   ↓ 流阻 ∝ r⁻⁴，几何长度 ∝ 格距
单段流阻 +52%
   ↓ 串联累加
总压降 16 倍
```

（`calibrate.py` L227–230 的注释给出这三个数，并指向 `DEFECT_REMEDIATION_PLAN.md` §10.9。）

关键在于**没有任何一步报错**。两次运行都成功，两个数都「看起来合理」，只有把两次输出放在一起才会发现 16 倍。

## 为什么难发现

1. **量纲相同。** 两个都是 mm，不是「米和毫米」那种一眼能看出的错。
2. **量级接近。** 1.0 和 0.9 差 10%，肉眼看 CSV 不会警觉。
3. **误差被非线性放大。** `r⁴` 把 11% 变成 52%，串联把 52% 变成 16 倍。检查单段会发现「差不多」，检查总数才会发现「全错」。
4. **默认值接住了错误。** 调用方省略 `pitch_mm`，函数用默认 1.0 兜底，于是「忘了传」和「故意用 1.0」在代码里长得一模一样。这是 [FM-3 参数没传下去](/notes/fm-3-params/) 的合谋。

## 修复：不是合并，是分层

正确做法不是把两个数合成一个（那样会把「方程离散尺度」和「封装映射系数」两个概念一起藏起来），而是：

1. 给每个常数写上它属于哪一层（`paper_grid_mm` 的 docstring L232–240 就是这么干的，还专门写了「the naive single source of truth fix would be wrong」）。
2. 真实单位只留一个入口：`paper_grid_mm(grid)`，它从 `PACKAGE_MM` 反推 0.9，不重复书写。
3. 入口处自洽断言：`assert abs(i7_14700k(grid).grid_mm - grid_mm) < 1e-12`。
4. 边界处拒绝歧义：`tree_dp_pa` 见到 `grid_mm == PITCH_MM` 直接 `raise ValueError`（L452–457）。

## 自己写代码时的检测清单

- 全局搜同一个数字出现几次：`grep -n "0\.9" *.py`、`grep -n "= 1\.0" *.py`，每处问一句「它是谁的尺子」。
- 任何进入 `r⁴`、`r⁻⁴`、指数、对数、平方根的参数，都要单独核对——这些位置把 10% 放大成 50%。
- 任何用默认值兜底的物理参数，都当作可疑对象处理。
